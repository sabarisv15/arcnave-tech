| LW-56 | **libheif-js (LGPL-3.0) in the backend image.** Package `libheif-js` 1.23.5 (npm, licence field `LGPL-3.0`, LICENSE file = GNU LGPL v3), pulled in by `heic-decode` 2.1.0 (ISC), which `backend/package.json` declares. It is libheif compiled to WebAssembly with Emscripten; the build also contains the libde265 HEVC decoder (LGPL-3.0; its symbols are in the bundle). **How it is linked:** not a native shared library. The WebAssembly is embedded in a JavaScript file (`libheif-js/libheif-wasm/libheif-bundle.js`, loaded through `libheif-js/wasm-bundle`), shipped unmodified inside `node_modules` in the backend container image, and loaded at run time only inside the isolated parser child process (`backend/src/services/attachments/derive.ts`, `normaliseImage`). ArcNave does not modify it and does not distribute the image to customers (it runs as a hosted service). **Why it is needed:** iPhones save photos as HEIC/HEIF by default; Stage 9 TYPES lists HEIC, and the image pipeline must decode it to make the normalised JPEG/PNG copy every model is sent (ADR-0063 Decision 4). **Questions for the lawyer:** (1) For a hosted service that does not ship the image to customers, are there LGPL-3.0 obligations at all (no "conveying")? If the image or an on-premise build is ever given to a customer, what must ship with it (licence text, the libheif/libde265 source or a written offer, the ability to replace the library — is an unmodified npm package in `node_modules` "replaceable" for LGPL-3 §4(d))? (2) Is a THIRD_PARTY_NOTICES entry (LW-41) enough for the hosted case? (3) HEVC patents: decoding HEIC uses HEVC, which is covered by patent pools (Access Advance, Via LA). Does decoding user-uploaded HEIC on our servers need a patent licence, or is it covered by the uploading device's licence, and does that change if we ever encode HEVC (we do not today)? | tech-build.3 D0b, ADR-0063 Dependencies |

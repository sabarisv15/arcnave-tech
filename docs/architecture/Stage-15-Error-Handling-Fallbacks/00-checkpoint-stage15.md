## Locked decisions (one line each)
- **ER-1:** SDK retries OFF (Anthropic `max_retries=0`; google-genai no retry options); ArcNave retry matrix is the only retry.
- **ER-2 retry matrix (before first token only):** transient = 429 (not spend cap), 500/502/503/504, 529, connection/408/409 → ≤2 retries, backoff 1 s → 2 s + full jitter, cap 8 s; provider Retry-After honoured up to 10 s (N) else straight to fallback; never retry 400/401/403/404/413, spend-cap 429, refusal, safety block, 499.
- **ER-3 mid-stream:** no silent retry after partial text; one stream-recovery attempt (new user message with partial + "continue"; Claude documented, Gemini LV-1) appended as continuation; failure → keep partial, finish code `interrupted`, "answer was cut short" + Continue (S13 VD-3); partial tool_use/thinking → restart that step from checkpoint.

- **ER-5 Redis degraded:** relay best-effort (acked writes can be lost); seq gap → DB snapshot; DB fencing decides commits; Redis down >5 s (N) → client polls DB every 2 s (N), local rate limits, policy from DB – chat never blocks.

## Doc-sync 2026-10-04 (Stage 21 Task 0.7 review – ER-1 detail)
- **ER-1 google-genai:** "retries off" is set **explicitly**: `HttpOptions(retry_options=HttpRetryOptions(attempts=1))` (attempts counts the original request; 0 or 1 = no retries). Reason: Google's retry-strategy page documents automatic retries by the Python SDK, while the locked SDK 2.28.0 makes exactly one attempt when no retry options are set (`retry_args(None)` → `stop_after_attempt(1)`, read in the installed source). A guard test asserts that the client's sync and async retry objects stop after one attempt, so an SDK upgrade cannot change this silently. Anthropic side unchanged (`max_retries=0`). The Model Gateway (Phase 1) uses the same construction.

## Doc-sync 2026-10-04 (Stage 21 Task 0.8 review – LV-77, LV-18)
- **ER-1 verified (LV-77 PASS):** CI tests count requests at a local stub – our Anthropic and google-genai clients send exactly one request on 429 and on 503; controls prove the stub sees retries (Anthropic default 3 requests, google-genai `attempts=3` → 3).
- **ER-2 detail from LV-18 (Claude on Vertex, quota 429):** the error is Google-style – HTTP 429, `RESOURCE_EXHAUSTED`, text "Quota exceeded for …", **no `Retry-After` header and no Anthropic request id**. ## Doc-sync 2026-10-11 (Stage 21 Task 1.10 Part 1 review)
- **ER-1 – a hidden SDK re-send:** google-genai 2.28.0 sends async calls through aiohttp whenever aiohttp is importable (it is – Cloud SQL connector) and on a connection error sleeps 1–10 s and sends the request a **second time**, outside `HttpRetryOptions` (`_api_client.py` `_async_request_once`). Rule for every google-genai user: hand the SDK our own `httpx.AsyncClient` (`AsyncHTTPTransport(retries=0)`, explicit timeout, `trust_env=False`) + `HttpRetryOptions(attempts=1)`; guard tests prove one request and no sleep per call (stream, unary, cache list / create / update). `apps/lvrunner` has the same exposure (its clean-up task); the SDK's file-upload loop has its own retry (files task).
- **ER-3 – a stream without a finish reason:** a Gemini stream that ends after text with no finish reason (or `FINISH_REASON_UNSPECIFIED`) is a failure after the first text → `failed` / `interrupted`, partial kept; without text it is transient (ER-2 retries, then fallback). An unknown non-empty reason with text stays `done` (kind `other` in the turn stamp, WARN). Claude: a stream that ends after text without a stop reason – the same.
- **Blocked list:** finish reason `MODEL_ARMOR` (REST reference; unknown to SDK 2.28.0) → `blocked`, with SAFETY / PROHIBITED_CONTENT / SPII / BLOCKLIST / RECITATION, any prompt `block_reason` and Claude `refusal`.
- **ER-4 after a fallback:** the next model gets its own first-token timer (its profile's N-43 value); the turn deadline (N-43 10 min) bounds the whole; once the deadline has passed no retry and no fallback hop is started.
- **ER-2 quota-0 – known limit:** recognised by the "Quota exceeded for …" wording (LV-18); an ordinary per-minute 429 with the same wording is also treated as `quota` (no retry, fallback, ERROR line, one breaker failure). Watched at the dev run and the staging load test.
- **ER-13 breaker as built:** every attempt holds an admission and gives it back once (also when cancelled in a retry wait); a call admitted before the breaker last opened cannot change a half-open breaker; an empty 200 answer counts as a success.
- **Cache errors (ADR-0004 as built):** a refused cached call is re-sent uncached at once; the cache is forgotten only when that re-send gets through (a 403 that is not about the cache never recreates it turn after turn); a cache admin call is bounded by N-74 10 s.

## Doc-sync 2026-10-12 (Stage 21 Task 1.11 brief – Turn Executor: ER-3 recovery, ER-4 SIGTERM, ER-7 queue)
- **ER-3 one stream-recovery attempt (designed in Task 1.11):** after a failure that follows the first text (`GatewayCutShort`), one continuation request to the **same served model** (pinned – no fallback hop; ER-2 retries before its first new text; its own N-43 first-token timer; same turn deadline), its text appended to the same stream and answer. The continuation is a new user message (Anthropic "Error recovery", Claude 4.6+); an adapter that must keep roles alternating joins it to the current user turn as its last text block; never an assistant prefill. Text from a versioned prompt-kit file (`recovery_prompt_version` stamped). Counted in `turns.continuations` (≤ 1). Failure of the continuation → `failed` / `interrupted`, all text kept (as locked). A dev fault is never applied to a continuation. Gemini quality = LV-76.
- **ER-4 SIGTERM – reviewer clarification (no change of the locked outcome):** the **attempt** is interrupted, not the turn: the executor cancels the source read, flushes its buffer, releases the lease and answers 500; the turn stays `running`, so FD-1 keeps the chat busy until a Cloud Tasks delivery resumes it, the user stops it (ended `stopped` at once), or the resume window (N-73 60 s) ends it `interrupted` with the partial kept. Same after a crash (the lease runs out by itself). Budget 5 s of Cloud Run's 10 s; flush / release in the new N-45 transaction kind `shutdown` (2 s).
- **AS-D3 "1 retry that resumes from checkpoint":** enforced by `turns.resumes` (≤ 1), not by Cloud Tasks' attempt count. A resume with earlier text continues it with the checkpoint's served model (counts as the resume, not as the ER-3 continuation); without text it generates normally. R14: checkpoint v1 = metadata only; an unreadable version is not taken (500 – a later delivery may land on a matching revision).
- **ER-7 finding (Cloud Tasks RetryConfig reference, reviewer read 2026-10-12):** "Cloud Tasks stops retrying only when `maxAttempts` and `maxRetryDuration` are both satisfied" – N-44's turns values (2 / 20 min / 5 s) give several deliveries within 20 min, not one retry. N-44 unchanged in Task 1.11 (the database guards correctness: every later delivery ends `not_queued` → 2xx); `maxRetryDuration` re-decided after the dev run. The executor answers 500 (not 503) when a retry is wanted – a 503 / 429 makes Cloud Tasks slow the whole queue.
- **Enqueue (api, after COMMIT):** `google-cloud-tasks` with its own retries off (`retry=None`, explicit timeout); our only retry: ≤ 2 on UNAVAILABLE / DEADLINE_EXCEEDED / INTERNAL / RESOURCE_EXHAUSTED (N-73 additions); `ALREADY_EXISTS` = success (hashed task name = the turn id's digest); a final failure leaves the turn `queued` → dispatch grace → `interrupted` until the worker's sweeper exists (FG8 deferred).
